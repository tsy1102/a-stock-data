> 本文件记录经当前代码和测试核实、对跨模块维护仍有帮助的架构约束。它不替代用户当前要求、运行行为或 `AGENTS.md` 操作规约。
> 初版：2026-09-03。原则不适用或已过时时，应修订原则及依赖项，不要求实现迁就过期设计。

代码修改前置调查统一遵守 [`AGENTS.md`](../AGENTS.md) §8.1 的事实门。本文件解释架构原则，不另设一套重复的前置清单。

## 1. 系统本体：什么是"统一层"

### 1.1 统一层是一个两层网关，不是一个大对象

```
生产脚本 (main.py / get_*_report.py / sc_report_runner.py)
      │
      ├── Tier1 门面 ─── get_canonical_stock_data()  [core/data_provider.py]
       │                  · CanonicalStockData：统一字段合约
       │                  · 源选择 + fallback + 单位归一化 + 逐字段来源/有效日期溯源
      │                  · 所有报告/策略引擎共用的"横向数据"
      │
      └── Tier2 适配器 ── sc_datasource / sc_fuyao / tdx_client.tdx_get_*
                          · 专精深水数据：CYQ 筹码、F10 财务、涨停梯队、
                            龙虎榜、行业 L2、宏观流向、竞价盘口
                           · 按适配器职责处理缓存、单位归一化、限流与来源溯源
                          · 报告特有的"纵向数据"
      │
原始客户端 ─── _get_tdx_client() / sc_network.em_get / sc_fuyao._fuyao_raw / 裸 requests·httpx
              ↑ 仅允许出现在 stock_common/ 与 core/tdx_client.py 内部
```

### 1.2 关键边界：不要把专精数据塞进 CanonicalStockData

把 CYQ / F10 / 龙虎榜塞进 `CanonicalStockData` 会造出 **god-object**：
`CanonicalStockData` 保存共享的横向数据和统一溯源元数据。混入报告特有数据会过度耦合，
且 fallback 一致性反而更难做（而这正是统一层要解决的原始问题）。

字段、来源和日期元数据的实际成员由代码与契约测试定义；不要在原则文档中维护易过期的属性数量或路由摘要。

> **Tier2 适配器就是统一层的"专精面"，它不是绕过统一层。**
> 各适配器按数据职责落实所需的归一化、缓存、限流与溯源；具体策略以实现和 A4 为准。

## 2. 架构原则

> 下列原则是当前设计约束，可以依据代码、测试和用户要求复核与修订。只有确认实现偏离仍适用的原则时，才按 A8 记录。

### A1 — 数据访问收口（Access Chokepoint）

生产脚本获取外部数据，必须经过 Tier1 或 Tier2 的**公开函数**。
原始客户端（`_get_tdx_client()`、`sc_network.em_get`/`tencent_get`/`_quick_request`、
`sc_fuyao._fuyao_raw`、裸 `requests`/`httpx`）**仅允许**在 `stock_common/` 与
`core/tdx_client.py` 内部出现。

- **理由**：集中治理源选择、限流、缓存、可观测。分散直连 = 风控失效 + 口径不一。
- **自动化验证**：`scripts/verify_data_access.py`
- **已接受例外**：DEBT-002（历史探针保留原始访问，验证闸门明确排除）

### A2 — 单一规范字段（Single Source of Truth）

每个业务语义在契约中应有一个规范字段和一致口径，避免重复别名。若兼容或外部契约确实要求保留别名，应明确其用途与范围，不得把别名当作独立字段或独立验证证据。

- **理由**：冗余别名会让下游误以为是独立口径，从而产生**假的交叉验证**。
- **检查方式**：改动字段契约时按 `AGENTS.md` 事实门检查 schema、所有消费者与测试；当前没有专门的冗余别名扫描器。
- 历史处理记录见 `DEBT_LEDGER.md`，不在本原则中维护当前字段清单。

### A3 — 边界归一化（Normalize at Boundary）

单位与口径必须在进入 `CanonicalStockData` **之前**统一。数值字段的契约说明应标明单位，避免同一契约里的单位歧义。

- **理由**：契约是消费方的唯一依赖，单位歧义会静默放大 10 倍级错误。
- 历史处理记录见 `DEBT_LEDGER.md`；当前单位以适配器输出和契约测试为准。

### A4 — 缓存只存有效值 + 财报期识别（Cache Integrity）

① 失败、无效或暂时不完整的结果不入缓存；空集合是否有效由来源契约和 `valid_if` 明确判定；
② 财报类缓存 Key 必须含 `report_date`（报告期切换瞬时刷新）；
③ 新增网络接口必须明确数据缓存策略，包括 TTL、缓存键、空结果和新鲜度；不缓存时需记录具体理由。
④ 交易日数据缓存必须按项目交易日历写入绝对失效时间；文件修改时间只用于延迟磁盘清理，不能决定缓存是否可读。
⑤ `valid_if` 拒绝已有缓存时，必须精确淘汰该键，避免坏值留在缓存中并让每次调用重复请求上游。

- **理由**：空结果缓存会把暂时性缺数延长为缓存期内的持续缺数；报告期字段需要区分不同报告期。
- **检查方式**：按 `AGENTS.md` §9 运行相关缓存模块的契约测试。
- **示例**：DEBT-006 记录了 `get_em_quote_full` 不缓存的具体原因，说明缓存策略可以按接口明确选择。

### A5 — 契约无孤儿（No Orphan Fields）

运行时契约字段应有明确消费方。新增字段前先确认消费方；如果字段暂时只用于明确的后续工作，应记录用途和启用条件，避免无目的地扩张契约。

- **理由**：只加不用的字段会让契约失去权威性（无法区分"重要但未接"和"废弃"）。
- **检查方式**：当前没有通用的契约消费者覆盖闸门；按 `AGENTS.md` 事实门检查调用方和测试。
- 历史处理记录见 `DEBT_LEDGER.md`。

### A6 — 缺失即缺失（Absence ≠ Zero）

0 不是中性值，常是有效取值。缺失数据默认保持缺失并排除在计算之外；只有来源契约或业务规则明确证明“缺失即零”时才可填零，不能用 `x or 0` 代替判断。

- **理由**：把缺失降级为 0 会让"无数据"伪装成"极小值"，扭曲排序与阈值判定。

### A7 — 文档与代码同真（Doc-Code Coherence）

字段身份、语义、单位或映射发生变化时，应同步更新相关 registry、适配器、消费者、生成视图和测试。与字段契约无关的代码改动不要求改字典。

- **理由**：过去出现过字段文档定案与实际运行行为不一致的情况。
- **自动化验证**：`scripts/verify_sync_check.py`
- 历史处理记录见 `DEBT_LEDGER.md`。

### A8 — 不静默偏离仍适用的原则

确认某项现行实现偏离仍适用的 A1–A7 后：

1. 修复实现；或
2. 在 `docs/DEBT_LEDGER.md` 登记这个具体偏离、技术原因、影响范围及处置计划或接受理由。

若原则已过时或与用户当前要求冲突，先修订原则及受影响的测试和文档；不得把过期规则当作事实，强迫实现迁就。

确认偏离仍适用的原则后，不得只以"改动大/风险高"为由忽略它；需要在修复和记录具体偏离之间作出决定。

- **台账口径**：逐条债务状态是当前状态依据；数量仅是可选快照，不作为绩效指标。
