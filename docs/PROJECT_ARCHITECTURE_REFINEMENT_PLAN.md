# 全项目架构与维护整改方案

> 状态：整改阶段全部完成并通过验收；版本升至 17.6，按用户授权进入最终提交与推送。
> 基线日期：2026-10-21。项目版本：17.5.11。

## 1. 目标与边界

目标是在不改变已确认的数据含义、来源顺序、限流策略、报告结论和缓存契约的前提下，降低核心脚本的理解成本，避免候选“机器完整”被误读为“人工已审”，并让每次重构可验证、可回退。

本方案不授权删除历史采集/碰撞证据，不授权更改主字典或字段注册表语义，也不默认执行真实网络请求。字段意义和来源身份必须由逐源证据裁决；架构重构不能顺带改变这些结论。

## 2. 审计基线与已确认问题

- 本轮修改后的离线套件：1,134 passed、1 skipped、52 个真实网络用例排除，29.62 秒；真实网络用例未运行。
- registry parity 当前通过：1,893 个字段、2,550 条来源路径、378 个多源字段；范围、投影、聚合语义和 field matrix 闸门均通过。
- 主要长模块约为：`scripts/capture_field_probe.py` 4,823 行、`scripts/collide.py` 3,797 行、`stock_common/sc_network.py` 1,910 行、`scripts/apply_collision_adjudications.py` 1,431 行。拆分时必须先绘出导入图、调用图和状态所有权，不能按行数机械切文件。
- `docs/axdata_interface_crosswalk.json` 约 15.4 MiB，字段和接口映射适合机器消费，但人工定位与审阅成本高；改造前需查明所有消费者与其对文件路径/顶层结构的依赖。
- 2026-10-20 碰撞报告记录 5,673 条候选明细机器对账完整；Markdown 摘要未展示这些明细，且逐目标人工处置仍未完成。机器完整、内容可读取、人工已审是三个不同状态，报告必须分别表达。
- 日采集的 `error_diagnostics` 仍以现有错误标记和文本为重要输入。文本规则可能因上游措辞变化而误分类，后续应引入结构化诊断，同时保留原始错误。
- 五大报告共享 `render_md_report`；当前有 Runner 装配/输出路径和部分章节、数值契约测试，但还没有五个生成器各自稳定正文的端到端输出契约。
- Black 命令行在本轮对两个小型测试文件的 `--check` 运行 60 秒无输出；改用 Black Python API 对同一文件集检查通过。格式结果已确认，但 CLI 卡住的根因仍待查，应纳入维护工具链整改。

## 3. 执行原则

1. **先立契约，再拆模块**：先固定公开函数签名、输入输出结构、错误状态、文件格式、缓存键和数据日期语义，再移动实现。
2. **一次只改一个边界**：每阶段只处理一个模块族；不同时重构采集、碰撞和报告输出。
3. **保留兼容门面**：CLI 参数、生产入口、适配器公开函数和生成文件格式优先保持不变；必要的迁移适配层要有明确移除条件。
4. **证据与状态分离**：原始事实、机器候选、自动规则结论、人工审阅状态分别存储，不用一项的完成状态代替另一项。
5. **无证据不改核心资产**：注册表与主字典每项写回都须引用来源路径、数据日期和裁决证据；聚合字段的 verified 状态不能覆盖逐源未验证状态。
6. **可回退、可比较**：重构前后使用同一离线样本和黄金输出；每个阶段独立提交/检查点，失败时只回退当前阶段。

## 4. 分阶段实施

### 阶段 0：基线、范围与数据保护（本轮执行）

**内容**：确认 Git 工作区、测试/类型/格式/注册表基线；更新过期 parity 记录；修复测试类型断言；补共享报告写入器输出测试；把过期的 f107/f118 待办改为逐来源身份问题。

**验收**：离线套件及适用闸门通过；报告数字与实际命令一致；主字典、字段注册、生产采集和报告逻辑未被无证据改写。

### 阶段 1：可观测诊断与报告输出契约

**范围**：错误诊断结构、五个报告生成器输出检查。

- 定义稳定的诊断字段，例如 `code`、`phase`、`retryable`、`risk_family`、`host`、`http_status`、`raw_error`；保留原始错误文本，暂不改变重试/熔断决策。
- 建立五个报告入口的代表性离线输出契约：章节结构、数据缺失占位、来源/日期标注、Markdown 表格和文件编码；对时间、随机值及高波动数值做规范化，避免易碎的整文件快照。
- 验证每个 Runner 的成功、空数据和生成异常状态分别对应正确的文件/结果状态。

**验收**：所有诊断状态都有明确枚举；旧 `error_diagnostics` 与新结构可逐项对账；五大报告各至少有一条实际生成器输出测试；真实网络请求数为零。

### 阶段 2：候选审阅与裁决状态闭环

**范围**：碰撞候选的人工/自动审阅状态，不改候选数学算法和 L1 阈值。

- 使用稳定候选标识，将来源路径、方法、日期窗口、样本资格、证据文件和方法版本绑定起来。
- 采用显式处置枚举：`unreviewed`、`duplicate_grouped`、`insufficient_evidence`、`needs_external_evidence`、`accepted_for_adjudication`、`rejected`；记录处置时间、理由和证据引用。
- 报告分开展示候选生成完整率、身份校验、人工审阅覆盖率和待处理数量。5,673/5,673 只能代表机器清单完整，不能代表完成审阅。
- 允许按重复等价组批量处置，但必须保留每个成员到代表候选及原始证据的反向追溯。
- 主字典写回仍走现有裁决流程；审阅台账本身不能直接升级字段状态。

**验收**：同一报告重跑结果幂等；任何候选均可追溯到原始证据；摘要与 JSON 的生成数、审阅数和剩余数一致；无“摘要为空但宣布人工审阅完成”的状态。

### 阶段 3：碰撞引擎渐进拆分

**范围**：`scripts/collide.py` 及其关联状态/报告函数。

建议按稳定职责拆为：归档加载与身份校验、交易日窗口与样本筛选、值归一化与方法候选、候选评分/去重、状态读写、报告序列化。具体模块边界须先以调用图和真实共享状态确认。

**迁移方式**：`scripts/collide.py` 暂作 CLI 兼容门面；先搬纯函数，再搬无副作用序列化，再搬状态管理，最后才调整候选编排。每批迁移比对固定历史样本的 JSON 规范化摘要和 Markdown 章节集合。

**验收**：CLI 输出路径、选项、退出码和候选结果不变；日期资格与交易日窗口结果逐样本一致；collision state 无丢失或重复；全量离线套件、报告完整性闸门通过。

### 阶段 4：采集器拆分与网络状态单一所有权

**范围**：`scripts/capture_field_probe.py`、`stock_common/sc_network.py` 和采集适配器。

- 先画出 source registry、请求入口、域级限流桶、熔断状态、缓存写入和 raw 归档的所有权图。
- 将源配置、请求调度、响应验证、日期/新鲜度检查、raw 归档和元数据报告拆成独立职责；采集入口保留现有 CLI 与 orchestrator 行为。
- 网络层按传输、限流、重试/熔断、端点策略分开；一个 host/risk family 只能有一份限流与封禁状态，禁止为了拆分复制 limiter 或 fallback 请求。
- 失败重试按错误分类设白名单；403/429/封禁不重试，端点不确定时不得自动并发探测。

**验收**：不改变每日源/字段覆盖范围；相同输入的采集计划、请求预算和落盘身份一致；429/403 的停止行为有离线测试；所有临时文件继续落 `.tmp/`；不运行未授权实采。

### 阶段 5：五大报告模块化与输出质量

**范围**：`get_sht_report.py`、`get_med_report.py`、`get_lng_report.py`、`get_val_report.py`、`get_mak_report.py`。

- 先对章节、字段、来源、日期、缺失占位和计算公式建清单；不改变金融逻辑，仅建立输出契约。
- 把纯渲染/格式化逻辑移到稳定的报告呈现层；数据请求仍走统一层公开接口，章节计算仍保留在各报告策略层。
- 逐个报告迁移：SHT → MED → LNG → VAL → MAK；每个完成后对真实历史报告抽样审阅，避免全仓一次性替换造成章节损失。

**验收**：章节顺序和必需章节集不丢失；缺数明确显示，不伪造零值或源故障结论；有效日期、来源和单位标签不退化；Markdown 链接、表格和 UTF-8 输出通过契约测试；异步故障仍按各 Runner 现有回退约定处理。

### 阶段 6：大体积映射文档与历史证据治理

**范围**：AxData crosswalk 与历史研究/采集归档。

- 先枚举消费者、外部引用、schema 和生成器，再决定是否拆分；优先拆为按接口族分片的可审阅源文件，并生成兼容索引/汇总视图。
- 保持每个接口、字段出现项、证据链接和未知/重复/未验证关系无损；生成结果必须确定性排序。
- 用接口数、字段出现项、关系分布、引用可达性和 SHA-256/规范化摘要做拆分前后对账。
- 历史采集、raw、备份或报告只有在重复性、引用关系和证据价值逐项确认后才能制定保留期；不以文件大小或“旧”作为删除依据。

**验收**：257 个接口与 3,343 个字段出现项（以当时 crosswalk 基线为准）拆分前后数量与内容摘要相等；无断链；旧格式的消费者兼容或迁移完成；没有未经确认的历史证据删除。

### 阶段 7：维护自动化与文档收口

**范围**：开发检查、模块索引、架构文档和债务台账。

- 把语法、类型、格式、离线测试、数据访问、字典同步、canonical contract 和 parity 纳入统一离线入口；网络测试仍独立且显式启用。
- 单独定位 Windows 下 Black CLI 长时间无输出的原因；若不是环境启动故障，则为仓库增加快速、可重复、同配置的格式闸门，并验证失败退出码与 CI/本机结果一致。
- 对新增模块添加责任人/契约/调用者索引；删除过时指令时先做全仓链接与命令引用检查。
- 维护 `DEBT_LEDGER.md` 的真实偿还状态；修复完成即关闭对应条目，不能只改文案关闭债务。

**验收**：项目支持的 Python 环境可以按 README 安装依赖并运行离线套件；格式检查能在有界时间内完成并准确报告失败；检查入口在 Windows PowerShell 5.1 语法下可解析；若仓库配置 CI，CI 应调用同一入口；文档中的命令、版本、测试数量和文件链接与实际仓库一致。

## 5. 风险控制与停止条件

| 风险 | 控制方式 | 停止/回退条件 |
|---|---|---|
| 拆分时改变交易日、来源或字段语义 | 冻结契约与固定历史样本逐项比对 | 任一来源路径或有效日期结果变化，暂停该阶段并回退 |
| 多份限流器/熔断状态导致过量请求 | 绘制状态所有权图，迁移时保持单实例 | 请求预算、host 状态或停止行为不一致，禁止接入 |
| 报告章节丢失或假报成功 | 各报告实际输出契约和缺失样本测试 | 必需章节缺失、空文件被报成功，阻断阶段 |
| 候选状态误标“已审” | 单独计数机器完整和人工处置，所有处置留证 | 数量无法对账或结论无法回溯，报告标记 incomplete |
| 大 JSON 拆分时丢记录或断引用 | 确定性生成、数量和内容摘要对账 | 接口/字段数或摘要不一致，保留原文件并回退 |
| 删除旧证据破坏研究链路 | 先做反向引用和唯一性盘点，独立审批清理 | 找不到完整替代证据或无法证明无消费者，禁止删除 |

## 6. 每阶段交付格式

每阶段开始前先列出目标文件、导入者/调用方、数据契约、缓存影响、测试影响和回退点。交付时报告：改动清单、基线与结果指标、离线验证、未验证项、注册表/主字典是否改动、归档是否变动。除纯文档计划外，不把“测试超时”写成通过。

建议指标至少包括：全量离线通过数与耗时、registry/parity 数量、采集请求预算与源状态、碰撞候选机器完整率/人工审阅率、五大报告必需章节通过率、重构前后文件行数与依赖边数量。

## 7. 待审核的实施顺序

依次执行：阶段 0 → 阶段 1 → 阶段 2 → 阶段 3 → 阶段 4 → 阶段 5 → 阶段 6 → 阶段 7。阶段 0 已完成；用户已批准全部实施。每一阶段须保留验收记录，只有通过后才可进入下一阶段；发现行为差异时，先修复或回退当前阶段，不把失败带入后续阶段。所有阶段完成后再升版、全量验收、提交并推送。
