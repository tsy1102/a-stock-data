## 1. V17-2 — `sc_datasource.py` 拆包（7617 行 → 按域子模块）

### 现状
- `stock_common/sc_datasource.py` = **7617 行 / 162 个顶层 def/class**，是典型 god-module。
- 按函数名可清晰聚为 **~12 个业务域**：
  - 股东/十大流通：`_holder_fetch_*`、`holder_change`、`get_holder_structure`、`get_strategic_announcements`
  - 腾讯行情：`get_tencent_quote`(+async)、`get_em_batch_quotes`
  - 东财 datacenter：`eastmoney_datacenter`(+async)、`_em_filter`
  - K线/CYQ：`baidu_kline_full`、`get_cyq_distribution`
  - 行业/同业：`get_industry_peers`、`get_industry_comparison`、`get_industry_rank_from_zhb`、`_get_eastmoney_industry_sectors`、`get_stock_sector_rank`
  - 北向/沪深港通：`get_northbound_hold`、`get_hsgt_macro_flow`
  - 融资融券/大宗：`get_margin_trading`、`get_block_trade`
  - 分红/概念/舆情：`get_dividend_history`、`get_concept_blocks`、`get_ths_hot_reason`、`get_eastmoney_*_news`
  - 财报：`get_sina_financial_report`、`get_sina_balance_sheet`、`get_eastmoney_cash_flow`
  - 解禁/ROE：`get_lockup_expiry`、`get_roe_trend_series`、`get_gross_margin_and_roe`
  - 涨停池：`get_limit_up_pool`/`_broken`/`_down`/`_yesterday`、`ths_limit_up_pool`、`em_stock_monitor`
  - 资金流/L2：`get_board_fund_flow`、`get_history_fund_flow_120d`、`get_em_industry_l2*`、`dragon_tiger_backup`、`fund_flow_backup`
  - ZHB 本地库：`get_zhb_*`(约 18 个)

### 改动内容
将单文件重构为 **包** `stock_common/sc_datasource/`：**`__init__.py` 保留原文件「剔除函数体后的残体」（import 块 + 全部模块级状态 + 注释），末尾 loader 把各域子模块源码 `exec` 进本包共享 `globals()`**；域子模块 `_holders` / `_eastmoney` / `_quotes` / `_industry` / `_financials` / `_pools` / `_zhb` / `_misc` 仅含函数定义。对外 100+ 既有 import 站点 `from stock_common.sc_datasource import X` **零破坏**。

> **执行结果（2026-09-04 重做）**：未采用 §0 原拟的「`__init__.py` 作 Facade 重导出」——该路径首次尝试引入了 39 失败（命名空间注入使模块级状态成多副本 + 破坏 `mock.patch` 对内部调用的生效）。改为「共享命名空间 + 源码 `exec` 进同一 `globals()`」后，状态唯一、补丁对内部调用生效，全量回归零回归。详见 `CHANGELOG.md [V17.1.0]`。

### 难度
- **工作量：高**。162 个函数跨 ~12 文件搬迁，需同步处理：
  - **模块级共享状态**：`get_cache`/`set_cache`(stock_cache)、`_TENCENT_FIELD_INDEX`、`_FFLOW_HOSTS`、`TTL` 等常量/单例必须抽到中性叶子模块，避免子模块互引成环。
  - **async/sync 配对函数**（如 `get_holder_structure` / `get_holder_structure_async`）须留在同一子模块，否则跨文件引用易错。
  - 内部交叉调用（`sc_datasource` 内函数互调）在拆包后变成跨模块 import，需统一走 Facade 或相对导入。
- **风险：中**。纯"移动 + 重导出"不改变运行时行为，但 god-module 的隐式耦合（全局缓存、模块级可变 dict）若遗漏一处，表现为**偶发缓存串号 / 启动 ImportError**。必须配全量回归 + 启动冒烟。

### 收益
- **可维护性中高**：diff 可读性、定位成本、新人上手显著改善；后续字段破解改动落在小文件而非 7600 行巨石。
- **零功能/正确性收益**：不修任何 bug、不改任何口径。纯结构投资。

### 建议
✅ **推荐作为 17.1 唯一内容**。前提是"移动 + Facade 重导出"策略 + 全量回归闸门。若团队当前重心是字段破解收官与稳定，可暂缓（非紧急）。

## 2. V17-3 — `data_provider` 与 `sc_datasource` 职责合并

### 现状
- `core/data_provider.py`(2239 行) = **Tier1 门面**（`get_canonical_stock_data` 唯一数据入口，86 字段 frozen 契约 + `field_sources` 溯源）。
- `stock_common/sc_datasource.py`(7617 行) = **适配器层**（东财/腾讯/TDX/ZHB 原始取数）。
- 二者分层是 `ARCHITECTURE_THEORY.md` **公理 A1（数据访问收口）** 的刻意设计：门面在上、适配器在下，裸客户端（`tdx_client`/`sc_fuyao`）仅允许在 `stock_common/` 与 `core/tdx_client.py` 内。

### 改动内容（字面理解）
把门面与适配器合并为单一模块 → **~9800 行** mega-file。

### 难度 / 风险
- **高 × 高**。合并会：
  1. **直接违背 A1 分层原则**（架构倒退）。
  2. 制造无法导航的万行文件（比现有 god-module 更糟）。
  3. 破坏现有 lazy-import 循环依赖管理（见 V17-4）。
- 无任何功能收益，且增加回归风险。

### 收益
- **负**。合并消灭了"A1 闸门可审计的分层"，使 `scripts/verify_data_access.py` 的收口校验失去结构依托。

### 建议
❌ **不做**。若实际痛点是"二者职责有重叠/重复"，应作为 **针对性 DEBT 条目**排查具体重复函数（如某字段两处都能取），而非整体合并。V17.0 重构已大幅厘清边界，本提案属 roadmap 旧提案（与 V17-5/6 同源的"前提已失效"类）。

## 3. V17-4 — 73 处 lazy import 改顶部 import

### 现状（已实测）
- `core/data_provider.py` 内有 **70 处**缩进的 `from/import`（主要为 `from stock_common import ...` ×24、`from stock_common.sc_datasource import ...` ×12、`from core.tdx_client import ...` ×13 等）。
- **根因是循环依赖**：`stock_common/sc_datasource.py:77` 在**模块顶层** `from core.stock_cache import TTL, cached, make_valid_if`；`stock_common/sc_capital_cache.py:22` 同样顶层 `from core.stock_cache import cached`。即依赖链 `core(data_provider) → stock_common(sc_datasource) → core(stock_cache)` 形成 **core ↔ stock_common 循环**。
- `data_provider` 用函数内 lazy import，正是为了在**导入期**切断这条环，避免 `ImportError` / 部分初始化模块访问崩溃。

### 改动内容（字面理解）
把 73 处函数内 import 提升到模块顶部。

### 难度 / 风险
- **中（工作量）/ 高（风险）**。直接提升级会触发循环依赖在导入期实打实报错（或静默拿到半初始化模块的属性 → 偶发 `AttributeError`）。当前能跑，正是因为 lazy 模式规避了它。
- 正确做法需**先**抽离共享叶子（如把 `TTL`/`cached`/`make_valid_if`/`_TENCENT_FIELD_INDEX` 等 core 与 stock_common 共同依赖的常量与 primitive 移到中性 `common/` 或 `core/primitives.py`，双方都只依赖叶子、互不依赖），**之后**提升级才安全。但那本身是比"73 处移动"大得多的前置重构。

### 收益
- **低**。仅改善"import 结构整洁度"与极轻微启动性能；不修任何 bug、不改任何行为。

### 建议
❌ **不盲目做**。lazy import 此处是**正确且必要的**循环依赖解耦手段，不是技术债。若确实想改善 import 卫生，应走"先抽离共享叶子模块（前置重构）→ 再提升级"的路径，且收益有限、风险前置高，**建议暂缓**。
