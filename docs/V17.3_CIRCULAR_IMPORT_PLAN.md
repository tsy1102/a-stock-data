## 一、用大白话解释"循环导入"是什么

模块加载像"打电话"：A 说"我加载前得先打通 B"，B 说"我加载前得先打通 A"——两人都没人先说完，死锁。

本仓库的死锁链（已实盘复现 `ImportError` 回溯）：

```
import core.data_provider
  → data_provider.py:64  from stock_common.sc_network import _fallback_logger
    → 触发 stock_common/__init__.py:259  from stock_common.sc_datasource import (...)
      → sc_datasource/__init__.py:700  from ._quotes import *   (及 :704 _zhb)
        → _quotes.py:20    from core.data_provider import get_concept_from_zhb
        → _zhb.py:13       from core.data_provider import get_amount_wan, ...
          → 回到 core.data_provider（此时只初始化到 line 64，get_concept_from_zhb 在 line 285 尚未定义）
            → ImportError: cannot import name 'get_concept_from_zhb' from partially initialized module
```

**为什么生产不崩**：应用入口先 `import stock_common`。此时 `stock_common` 包已进入 Python 的"正在加载"登记表（sys.modules）。当 `_quotes`/`_zhb` 回头要 `core.data_provider` 时，Python 发现 `stock_common` 包已在加载中、**不再重跑 `__init__`**，于是 `core.data_provider` 能顺利加载完 → 成功。

**为什么你直引 `core.data_provider` 会崩**：探针/新模块若先 `import core.data_provider`，Python 从零加载它，撞到 line 64 才第一次触发 `stock_common`（此前不在 sys.modules）→ 重跑 `__init__` → 上述死锁。

**一句话**：不是代码写错，是"谁先被 import"的顺序依赖。生产靠约定（先载 stock_common）规避；直引 data_provider 就踩雷。

## 二、真实依赖图（实测，非印象）—— 推翻"70 处 lazy 断环"旧认知

实测 `core↔stock_common` 跨边界**顶层**导入边（导入期环的唯一来源）：

| 方向 | 顶层边数 | 落点 | 是否构成问题 |
|---|---|---|---|
| `stock_common → core` | 12 | 11 条→`core.stock_cache`（**真叶子**，已验证零 stock_common/core 导入） | **安全** |
| `stock_common → core` | **2** | `_quotes.py:20`→`get_concept_from_zhb`；`_zhb.py:13`→5 个 ZHB 函数 | **问题边** |
| `core → stock_common` | 5 | 4 条→叶子工具（`_debug_log`/`_safe_float`/`UA`/`_quick_request`） | **安全** |
| `core → stock_common` | **1** | `data_provider.py:64`→`sc_network._fallback_logger` | **问题边（触发点）** |

→ **导入期环 = 恰好 3 条顶层边**（不是"70 处"）。

**关键澄清 — "70 处 lazy import 断环"是红鲱鱼**：
- 全仓函数体内（调用期）跨引：`core→stock_common` 72 处 + `stock_common→core` 64 处 = **136 处 lazy 导入**。
- 这些在函数**被调用时**才执行，彼时所有模块已加载，**不构成导入期环**，是跨边界调用的正常写法，也是项目既有的标准规避模式。
- 所以"136 处 lazy"不是症状、也不是"断环补丁"，而是健康代码。真正的环只在上面 3 条顶层边。

**另一关键澄清 — `core.zhb_client` 自身也引 `stock_common`**：
- `core/zhb_client.py:100` 顶层 `from stock_common import _debug_log`。
- ⇒ `stock_common → zhb_client → stock_common` **本身仍是环**。任何 `stock_common` 子模块若顶层引 `zhb_client`，照样触发死锁。

- 对照：`core/zhb_client.py:1814-1860` 也有**同名原始版**（无新鲜度门控）。
- 全仓真实调用方（排除 backups）：`core/data_provider.py`（内部 3 处）、`get_sht_report.py`、`stock_common/sc_datasource/_quotes.py`、`stock_common/sc_datasource/__init__.py`（re-export 链 line 1204）、`tests/*`。数量小、可控。

**结论**：这 6 个函数本来就"顶层干净、函数内懒引"，迁移成本极低；C 的爆炸半径 = 1 个新文件 + 6 次函数移动 + ~3 行 import 改点 + 保留 re-export。

## 四、重构方案（修正版）

### ✅ 方案 A（最小化·极低风险）— 断 data_provider 端唯一触发点
- **改动**：`core/data_provider.py` 删 line 64 顶层 `from stock_common.sc_network import _fallback_logger`；在 `_debug_log()`（line 68）函数体首行加该导入（`_fallback_logger` 全文件仅此一处使用）。
- **效果**：`import core.data_provider` 不再在顶层拉 `stock_common` → 死锁链断裂。re-export 链完全不动。
- **风险**：极低（1 行移动）。
- **残留**：`_quotes:20`/`_zhb:13` 两条边仍在，仅因"生产先载 stock_common"而**休眠**；若未来有人先直引 `_quotes`/`_zhb` 再加 data_provider，或测试入口改顺序，崩溃会复发。

### ❌ 原方案 B（已证伪，作废）
- 原设想：`_zhb.py:13` 改引 `core.zhb_client` 即可断 `_zhb` 臂。
- **证伪**：`zhb_client` 顶层引 `stock_common`（line 100），故 `stock_common → zhb_client → stock_common` 仍是环，**断不开**。B 在技术上无效，本条删除。

### ✅✅ 方案 C（架构级·修正为"抽叶子模块"，中低风险）— 真正消除环
- **核心认知**：要让 `_quotes:20`/`_zhb:13` 断环，目标模块必须**顶层不引 stock_common**。唯一满足条件的现成叶子是 `core.stock_cache`，但 6 个访问器需 stock_common（它们封装 stock_common 原语），不能落 stock_cache 而不变非叶。⇒ 正确做法是**新建一个真叶子 `core/_accessors.py`**。
- **改动（作用域明确、可控）**：
  1. 新建 `core/_accessors.py`：顶层**不**引 stock_common/core；把 6 个访问器原样迁入（其体已"顶层干净 + 函数内 `from stock_common import ...` / `from core.zhb_client import ...`"，无需改实现）。
  2. `core/data_provider.py` 改为 `from core._accessors import (6 个)`（保留其公开 API，内部调用方零改动）。
  3. `_quotes.py:20` → `from core._accessors import get_concept_from_zhb`（re-export 链 line 1204 经 `from ._quotes import *` 仍暴露该名，链不断）。
  4. `_zhb.py:13` → `from core._accessors import (5 个 ZHB 函数)`。
  5. 顺带把 A 的 line 64 懒导入一并做（data_provider 顶层彻底无 stock_common 跨引）。
- **效果**：`core↔stock_common` 导入期图**真正无环**，import 顺序完全无关，休眠脆弱点彻底消除。
- **风险**：中-低（非"高"）：函数已懒引结构化，移动机械；主要风险点 = re-export 链保持（已验证 `from ._quotes import *` 透传） + 5 个 ZHB 函数须保留**封装版（带新鲜度门控）语义**、不可误换成 zhb_client 原始版。需一轮回归测试。
- **额外收益**：消除"5 个 ZHB 函数在 zhb_client(原始)/data_provider(封装) 双份定义"的重复；明确跨边界访问器的归属层。
