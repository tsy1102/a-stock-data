# AxData 与项目字段逐项核实、去重补缺计划

> 制定日期：2026-10-09
> 目标：先用可追溯证据确认 AxData 接口、项目采集路径和主字典字段的真实对应关系，再决定字典去重、补缺及采集逻辑调整。
> 执行边界：本计划阶段不改生产采集逻辑，不把字段名相同直接当作语义相同，也不把 AxData 的接口目录当作已启用采集器目录。

## 一、现状与已取得的实测证据

- 项目依赖固定为 `axdata==0.1.4`。核对到的 AxData 上游 main 最新提交为 [`f8ce3cee9897`](https://github.com/electkismet/AxData/commit/f8ce3cee989717d79c7ad8f73b42f93c6dbd87e8)。上游清单定义 256 个 `source_request` 接口，另有 1 个 WebSocket 实时流；接口目录、可请求能力和实际采集器是不同层次。详见 [AxData 接口资产清单](https://github.com/electkismet/AxData/blob/f8ce3cee989717d79c7ad8f73b42f93c6dbd87e8/docs/data-interface-inventory.md)。
- 项目生产代码目前明确直接调用 AxData 的接口只有 `stock_shortline_indicators_tdx`。这不表示 AxData 的其他接口都被项目源完整替代；要逐项查实际端点、项目调用函数和字段口径。
- [AxData 接口交叉映射表](axdata_interface_crosswalk.md) 与 [逐字段 JSON](axdata_interface_crosswalk.json) 已列出 257 项、目录字段和基于字段名的候选交集。该表是核验索引，不是语义等价结论。
- 午间完成一次单股票实时样本：2026-10-09 12:35:28（AxData）和 12:35:33（项目），代码 `000001`。AxData 的 `stock_realtime_snapshot_tdx` 返回 41 个字段，项目 `core.tdx_client.tdx_get_quote_full` 返回 25 个字段。
- 该样本 4 个顶层同名字段为 `open`、`high`、`low`、`change_pct`；前三个值完全相同，`change_pct` 分别为 `-0.764007` 与 `-0.7640067911714759`，差异符合 AxData 保留 6 位小数的结果。另有可检验的别名/换算候选：`last_price` ↔ `price`、`pre_close` ↔ `last_close`、`change` ↔ `change_amt`、`ask1_price` ↔ `ask1`、`bid1_price` ↔ `bid1`；`amount` 与 `amount_wan` 相差 10,000 倍；`volume` 等于项目 `b_vol + s_vol`，且 `inside_volume` / `outside_volume` 分别与 `s_vol` / `b_vol` 数值相等。
- 上述数值关系来自单只股票、一次午间快照；响应没有独立的行情时间戳，不能据此确认所有时间段、股票或复权/单位边界都一致。主字典中多个 TDX 原始路径目前仍是 `unverified`，含义或单位为空，因此本次不直接改字典状态。
- 实测原始响应暂存于 `.tmp/axdata_project_live_sample_20261009.json`；它没有写入正式采集日期目录。AxData 的 TDX socket 在沙盒内被拒绝，获准在沙盒外运行后请求成功；这次失败是执行环境权限问题，不是源端封禁证据。
- 执行过程记录：临时探针首次预载 AxData 成功，但项目模块导入路径遗漏，导致该次 AxData 返回没有保存；修正导入路径后完成了上面的可复核配对样本。本轮实际发生 2 次 AxData 顶层请求、1 次项目 TDX 请求；探针没有自动重试循环。后续每轮先完成本地导入、参数和输出路径预检，再发一次请求并立即落盘。

### 2.3 每项的覆盖状态

在 JSON 交叉表中为每个 AxData `interface_id` 和每一项输出字段补齐以下最小记录：接口类别/调用方式、上游源码位置、请求参数、字段路径和类型、AxData 实际路由、项目 collector 是否 active、项目实际端点/适配器、原始返回路径、字典完整身份、数据日期域、缓存/限流、字段关系状态、证据等级和未决原因。关系状态必须区分“静态同名候选”“同源不同端点”“独立源同义”“单位/公式变换”“部分重叠”“同名异义”“AxData 独有”“项目独有”“无项目路由”“流接口”“未证实”。

完成全静态矩阵的机械对账：256/256 请求接口 + 1/1 流接口有状态；3,334/3,334 请求字段出现 + 9/9 流字段出现有映射或明确的无对应原因。无法仅凭源码解决的语义或值域问题列入实测队列，不用推测填满。

## 三、阶段安排

### 阶段 0：冻结基线和证据范围

1. 记录 AxData 版本、上游提交、接口目录数量、字段目录数量，以及当前主字典的来源字段数量和生成文件校验值。
2. 以只读快照备份 `field_registry.json`、字段字典生成文件、来源谱系和历史字段协议文档；备份保存在项目 `.tmp/`，逐项保存 SHA-256。只有新映射完整核对、生成 parity 通过后，才允许清理备份。
3. 保留现有 AxData 交叉映射作为静态目录基线；任何实测都另记实际采集时间、数据有效日期、调用接口、参数、股票代码和运行版本。

**交付物：** 可恢复的字段基线、版本与哈希清单、现有静态映射快照。

### 阶段 1：逐接口确认项目实际采集路径

对 256 个 `source_request` 接口和 1 个实时流逐项核查，不从同源家族名称推断接口等价。每项至少记录：

- AxData `interface_id`、provider、接口类别、调用模式、必选/可选参数、返回字段、请求或适配实现源码位置；
- 项目实际对应的采集器入口、具体函数、底层 Tier1/Tier2 适配器、原始端点或 TDX 命令、参数和返回结构；
- 是否被当前正式采集脚本调用、是否只在运行时/报表中使用、是否经过缓存、是否写入正式采集目录；
- 来源家族和独立性：AxData 聚合层与底层真实源分别登记，`market_sources` 等未确认聚合项不得算作独立源或已确认替代；
- 现有项目落盘文件或字典路径，没有对应项时写明“未接入”及理由。

接口关系采用明确状态：`direct_call`、`same_endpoint_candidate`、`same_provider_different_endpoint`、`family_candidate_only`、`no_project_route`、`stream_only`、`unverified`。只有追到实际调用和端点/协议证据后，才能从候选升为已确认关系。

**交付物：** 257 项接口到项目函数/数据路径的逐项映射；不得仅列 `collect_tdx`、`collect_eastmoney` 这类宽泛候选。

### 阶段 2：逐字段语义和字典身份对照

以 AxData 每个接口的每个返回字段为单位，连接到项目实际输出及 `field_registry.json.source_fields` 的完整 `(source, code path/identity)`，不能只以短字段名连接。逐项填写：

| 维度 | 核对内容 |
| --- | --- |
| 身份 | 原始字段名、完整项目源路径、canonical 字段、主字典状态 |
| 语义 | 描述、业务对象、分子/分母、聚合方式、盘口/累计/单笔含义 |
| 单位 | 元/万元、股/手、百分数/比例、价格精度、换算公式 |
| 时间 | 交易日/自然日、盘中时点/收盘值、T/T-1 基准、事件日期、统计窗口 |
| 结构 | 标量/列表/快照、证券代码格式、空值/缺失值、停牌或无公告时的返回 |
| 证据 | AxData 源码、项目源码、历史样本、实测代码/时间/数据日期、反例 |

字段关系分类：`exact_same_field`、`same_semantics_alias`、`same_semantics_with_transform`、`partial_overlap`、`same_name_different_meaning`、`axdata_only_candidate`、`project_only`、`not_applicable`、`unverified`。字段名一致只能生成候选，不足以确认 `exact_same_field`。

**交付物：** 字段级映射表；每个 AxData 输出字段都有项目字段身份或“无对应项及原因”。

### 阶段 3：受控实测，按源族和风险分批

1. 只采阶段 1/2 发现有实际对应候选、且与项目目标有关的接口；不为“覆盖 257 项”而逐个请求，也不触发 `--all` 或完整五大脚本。
2. 每轮按单一底层源族执行；优先复用项目公开适配器、既有令牌桶/限流器。按上游或项目已知限制设置间隔，禁止所有源共用一个臆测的固定频率。
3. 首轮选 1–3 只股票或一个明确日期；同一接口只发一次，探针不循环、不重试。遇到 `403`、`429`、连接封禁或连续空响应时停止该源族，不以备用接口快速补打。
4. AxData 与项目端使用同一证券、同一参数口径和尽可能接近的采集时刻；把 `collected_at` 与接口返回的 `as_of_date/trade_date/stats_date` 分开记录。交易数据按有效交易日比对，公告/新闻等事件数据按自然日比对。
5. 历史日线、财务、公告等按同一显式日期/报告期请求；盘中快照只和同一时点附近的快照比较。ZHB 短线接口必须先核实 ZIP 实际统计日期；当前缓存停留在 2026-09-30，不能把它当作 2026-10-09 的新鲜统计基准。
6. 原始响应先放 `.tmp/`，不覆盖 `docs/field_verification/{date}` 的正式采集文件；只有确认字段、时间戳、股票代码和状态元数据正确后，再转成正式验证证据。
7. 不在已知 push2/IP 封禁未恢复时采样东财 push2 家族。网络权限问题与源端返回的封禁/限流必须分开记录。

实测至少分为：接口可用性、返回结构、字段值映射、单位/公式、日期边界五类结论。静态代码能确定的字段不必反复请求网络；只有数据值才能验证的候选才安排实测。

**交付物：** 小样本原始快照、逐字段比较结果、源族限流与失败记录、无法确认项列表。

### 阶段 4：确定去重、保留和补缺建议

- **精确重复：** 同一底层源、同一端点/协议、同一字段意义和单位；确认项目是否重复采集，提出保留唯一请求路径的建议。
- **语义重复但独立源：** 业务含义相同而来源独立；保留来源身份作为交叉验证锚，不因字段 canonical 相同而删除源记录。
- **字段别名/单位变换：** 保留原始源字段和原始值，明确 canonical 与换算公式；不能将 `amount` 与 `amount_wan` 当作同一个原始值。
- **部分覆盖：** 逐字段标注接口覆盖范围；不要因为一个接口命中若干字典字段就宣称整接口被替代。
- **AxData 独有候选：** 先确认是否符合项目的未知字段破解目标、是否能持续采集、是否有稳定源/日期口径，再提出纳入主字典或采集器的建议。
- **无关或非目标信息：** 新闻正文、排行榜文字等不进入破解采集，除非字段研究明确需要上下文。
- **同名异义/口径冲突：** 保留各自来源路径，修正或补充含义、单位、日期口径和冲突证据，不强行合并。

注意：主字典是字段来源登记和证据核心。去重优先合并重复定义、重复 canonical 或重复请求路径；不删除仍用于来源溯源、对撞或独立性判断的原始 `source_fields` 记录。

### 阶段 5：按证据更新主字典及生成物

只有阶段 1–4 完成并逐项核对后，才提出实际字段更新：

1. 每个新增/修正字段必须带完整来源路径、含义、单位、数据日期规则、样本证据和状态依据。
2. 单次样本只能登记为候选证据；确认状态须满足源码/协议契约与跨证券、跨交易日样本的一致性，并检查停牌、空值、零值和盘中/盘后边界。
3. 先改权威 registry/谱系，再生成 `field_dict.md`、矩阵和相关索引；历史协议原文只读，不用生成器覆盖。
4. 逐项对比备份与新 registry：字段身份无遗漏、来源路径无丢失、单位/含义变更有依据；运行字典同步与 parity 闸门后才清理备份。

**交付物：** 主字典变更清单、生成文件、旧/新逐项 parity 结果和可回滚备份。

### 阶段 6：根据结果决定是否调整采集器

本阶段是阶段 1–5 的后续决策，不预先假定 AxData 应接入所有 256 个接口。仅对确认有价值且现有采集路径确实缺失的字段，评估新增或替换采集器；比较请求数、速率限制、可用性、缓存、日期质量和独立来源价值。若需修改生产调用，检查所有调用方、返回结构、缓存、来源血缘、版本号、README/CHANGELOG，并按项目验证入口完成测试、同步检查和代码审查。

## 四、证据等级与放行标准

| 等级 | 证据 | 可以得出的结论 |
| --- | --- | --- |
| E0 | 目录、接口名或字段名命中 | 仅登记候选 |
| E1 | AxData 与项目源码均已追到端点/协议、参数、返回路径 | 可以判断静态路径关系，不能仅凭此确认实时值等价 |
| E2 | 一次受控同代码样本，含原始值和采集时间 | 可以确认样本结构和初步换算候选 |
| E3 | 多证券、多交易日/报告期，含必要边界样本，且与源码定义一致 | 可提出主字典字段确认、去重或补缺 |

完成标准：

- 257 项均有明确的接口关系状态；256 个请求接口与 1 个流式目录项分开统计。
- AxData 所有已声明输出字段都映射到具体项目字段身份，或明确标为无对应/不适用/未接入并说明原因。
- 所有“重复”“替代”“补缺”结论至少有 E1；主字典状态升级或删除建议至少有 E3；跨源结论区分同源别名与独立源证据。
- 无因相同字段名而造成的错误合并；无未解释的字段、来源路径或日期样本丢失。
- 阶段 1–4 不改生产采集行为；完成报告后再据证据选择阶段 5/6 的实际修改范围。
