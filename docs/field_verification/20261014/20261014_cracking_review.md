### 来源范围必须按接口区分

`ulist239` 的 `f50` 与其他东财接口中同编号的字段不能合并释义。本次原始数据中，`ulist239.f50` 与 TDX 总资产稳定对应；注册表的 `东财-ulist239(np/get)::f50` 当前 `meaning` / `unit` 为空，而聚合字段记录会沿用其他接口的 `f50` 标签。`f51`、`f52`、`f55`、`f60` 也存在同类跨接口编号复用风险。后续应按 `(source, 完整 code path)` 补全，不应覆盖全局 `fXX` 含义。

## 排除项与质量问题

标准报告把下列字段对列为 L1，但原始响应显示命中主要来自双方都为零，非零样本反而不符：

- `tdx.finance_info.hgu` ↔ `ulist239.f190`：每个日期 19/20 命中，但 601288 的值为 `3073882.25` 对 `3`。
- `tdx.finance_info.hgu` ↔ `ulist239.f231`：每个日期 18/20 命中；601288 为 `3073882.25` 对 `0`，688589 为 `0` 对 `3`。
- `tdx.finance_info.bgu` ↔ `ulist239.f200`：每个日期 18–19/20 命中；000037 为 `26385.4492` 对 `2`，000011 为 `6760.52` 对 `2`。

这些结果不能证明字段语义相同。`collide.py` 当前检查字段是否为常量，但没有要求候选关系具备足够的非零/信息性样本；大量共同零值可满足 18/20 的 L1 门槛。建议后续为 L1 增加非零样本下限或零值占比拦截，再用反例测试保护。

另有 `zhb.full.pe_ttm` ↔ Tencent `[39]` 命中 96.25%、4 个交易日、80 组样本，是值得复核的近似关系；3 组不匹配尚未解释，本次不据此写入主字典。其余 L1 多为已登记关系的重复验证。

## 字典落地边界

本轮没有修改 `field_registry.json`、主字典或生产代码。原因是当前候选结论的**字段关系证据很强，但注册表的逐源身份口径与语义字段仍有待治理**：东财 ulist239 候选记录状态为 `verified` 但含义和单位为空，且同编号会从其他接口继承聚合标签；现有碰撞 adjudication 流程只接受报告左侧状态为 `unverified` 或 `candidate` 的目标，不能直接修订这些已标为 `verified` 的源字段描述。TDX 运行路径也使用 `finance_info.*` 前缀，而注册表保留了部分无容器前缀的字段身份。

应先完善“已存在的源字段补充释义/单位”的来源级证据写入方式，再将上表按 ulist239 的完整来源身份录入并运行生成器与 parity 校验。此次结论及原始数据路径已经保存，避免把字段编号跨接口混用或把零值候选写成定案。
