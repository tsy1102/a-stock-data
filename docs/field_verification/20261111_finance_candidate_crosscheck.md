# ELTDX 财务字段候选与报告期交叉核验（2026-11-11）

> 后续定案：本文记录候选阶段；两条股本标签冲突路径已于同日按 E3 来源内实证定案，当前含义和边界见[裁决记录](adjudications/20261111_eltdx_share_slots_empirical_semantics.md)。旧候选与数值审计保留为历史证据，不再代表当前注册状态。

## 目标与字段身份

本记录按来源和完整字段路径核验 `TDX-eltdx(适配层)` 的六个财务字段。拼音候选先行生成，后续再独立检查上游输出契约、单位、数据日期与公开报告；候选名称不能被数值猜测覆盖。

| 字段路径 | 拼音/英文候选 |
|---|---|
| `finance_batch[].fa_qi_ren_fa_ren_gu_raw_float` | 发起人法人股 / promoter legal-person shares |
| `finance_batch[].fa_ren_gu_raw_float` | 法人股 / legal-person shares |
| `finance_batch[].gu_dong_ren_shu_raw_float` | 股东人数 / number of shareholders |
| `finance_batch[].zhu_ying_shou_ru_raw_float` | 主营收入 / main-business revenue |
| `finance_batch[].ying_ye_li_run_raw_float` | 营业利润 / operating profit |
| `finance_batch[].zong_xian_jin_liu_raw_float` | 总现金流 / total cash flow |

`raw_float` 表示浮点数值表示，不提供业务含义。字段名候选、上游输出标签和实际数值语义分别记录。

## 来源与数据日期

- 项目固定使用 `eltdx==3.3.2`；采集路径是 `scripts/capture_tcp_collectors.py::collect_eltdx` → `finance_batch(..., include_raw=True)` → `raw_eltdx.json` 的 `stocks.<code>.finance_batch[0]`。
- ELTDX v3.3.2 [财务基础信息接口文档](https://github.com/electkismet/eltdx/blob/v3.3.2/docs/methods/7709-%E8%B4%A2%E5%8A%A1%E5%9F%BA%E7%A1%80%E4%BF%A1%E6%81%AF.md#L93-L132)列出这六个输出字段，前两项标为万股，股东人数未列金额单位，收入、营业利润、总现金流标为千元。其 [FinanceRecord 模型](https://github.com/electkismet/eltdx/blob/v3.3.2/src/eltdx/models/corporate.py#L207-L249)与 [0x0010 解码器](https://github.com/electkismet/eltdx/blob/v3.3.2/crates/eltdx-protocol/src/commands/corporate.rs#L449-L508)表明字段名由库的定序解码器赋予，服务端原始记录不携带中文标签。
- 审计了保留范围内 17 个采集日（2026-10-15 至 2026-11-10），每天均有 20 条 TDX、ELTDX 和 ZHB 样本。339 组同一股票、同一 `updated_date` 的 TDX/ELTDX 记录里，六个字段逐项按对应尺度完全一致；共 43 个唯一股票/更新日组合。600675 在 2026-10-30 的 TDX 与 ELTDX `updated_date` 分别为 2026-10-30 和 2026-10-29，故排除该错期配对。TDX 与 ELTDX 属同一 TDX 来源族，这只证明两种解析/序列化路径一致，不算独立来源。
- ZHB 的 17 份解析样本和 2026-10-15 起可读的日期化压缩包均已检视。ZHB `tipinfo` 不含这六项财务值；`tdxstat.cfg` 提供独立统计项（如扣非净利润、现金余额等），没有这六个字段的直连列映射。因此 ZHB 不能作为这六项的独立逐值锚点。

## 前两项：拼音候选保留，数据冲突待解

拼音及 ELTDX v3.3.2 文档均将 `fa_qi_ren_fa_ren_gu_raw_float` 指向发起人法人股、将 `fa_ren_gu_raw_float` 指向法人股，文档单位为万股。按项目规则先保留这两个中文候选及英文释义，再对原始值做独立检验。2026-11-10 样本中，两路径的值却分别贴近 2025 年 1—9 月归母净利润和营业收入；下表测试“实际返回值语义为上年同期财务金额、原始单位千元”这一替代假设，即 `raw × 1,000` 对比发行人正式报告的元值。此处“千元”是待验证假设，与上游文档的“万股”标签冲突：

这些跨规模样本包含亏损公司，且两字段分别落在“上年同期归母净利润”和“上年同期营业收入”上；差值符合千元量化与 `float32` 表示的舍入范围。以 920508 为例，负值直接反驳“股数”解释。留存样本的时间变化也支持这是随最新财报期间更新的比较数据：扫描 2026-10-15 至 2026-11-10 的 17 个日期化 `raw_eltdx.json`、20 只股票，观察到 21 次成对值更新，集中在 2026-10-21、10-23、10-28、10-29、10-30、11-02；记录的 `updated_date` 落在对应三季报发布窗口。最新样本中，第一字段 5/20 为负数。逐字段、逐股票的前后值及更新日期见[转移审计表](adjudications/20261111_eltdx_share_value_transition_audit.csv)。

因此，本轮将“上年同期归母净利润 / 上年同期营业收入（原始单位千元）”保留为两项的**强替代语义候选**，并把“发起人法人股 / 法人股”拼音及 ELTDX 模型标签置于候选列表首位、作为显式冲突证据。不能因这组数值吻合就覆盖字段名称，也不能因名称吻合就忽略样本反例。

### 解码路径复核及证据边界

- ELTDX v3.3.2 的 [FinanceRecord 字段表](https://github.com/electkismet/eltdx/blob/v3.3.2/docs/methods/7709-%E8%B4%A2%E5%8A%A1%E5%9F%BA%E7%A1%80%E4%BF%A1%E6%81%AF.md#L253-L329)明确把两个路径标为发起人法人股、法人股，单位万股；其 [0x0010 解码器](https://github.com/electkismet/eltdx/blob/v3.3.2/crates/eltdx-protocol/src/commands/corporate.rs#L3013-L3046)从 `record[7..143]` 取 136 字节主体，再按固定顺序把 `info[24..28]` 和 `info[28..32]` 解码为这两个 `f32` 路径。因此，样本矛盾不是 JSON 键别名或这两列之间的简单偏移错误；但解码器和它的字段表仍只定义 ELTDX 输出模型，没有独立证明通达信当前 0x0010 服务端槽位的业务语义。
- `injoyai/tdx` 等公开解析器也沿用同一组旧式协议字段名；它们说明该命名是长期协议解析约定，但共享相同协议来源，不能视为独立的当前槽位语义证据。
- 通达信当前[官方公式函数表](https://help.tdx.com.cn/gspt/docs/markdown/redword/functionlist.html)中 `FINANCE(3)` 是沪深京品种类型、`FINANCE(4)` 是行业代码，与旧 0x0010 解码字段不是同一套编号；不能用函数编号把当前公式字段反向套到上述原始槽位。

在没有通达信当前 0x0010 槽位定义或可核实的官方客户端逐值对照前，两项继续保持 `unverified`。现有值转移、财报同期值吻合、负股数反例与 ELTDX 拼音/模型标签必须并列保留；不把“报文槽位改义”“旧标签过期”“其他服务端数据行为”中的任一解释当作已证实根因。
