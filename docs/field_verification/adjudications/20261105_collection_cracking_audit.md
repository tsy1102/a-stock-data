## 已验证字段退出破解与写回闸门

- `collide.py` 将所有 `verified` 来源身份从破解目标排除。`collision_registry_context.py` 同时把这些身份加入 `verified_target_exclusions`；当含义/单位等锚元数据不完整时，字段仍不会重新成为破解目标，但也不会充当已知锚。缺口留给元数据复核。这修复了过去“已验证字段因元数据缺口重新入队”的逻辑问题。
- schema 5 写回器要求报告完整、`verified_anchor_only` 模式、候选属于 `actionable_L1` 的 L1/L1-U、样本满足日期与来源条件；还要求人工状态 `accepted_for_adjudication`。L4、方法线索、近似匹配和已登记映射复验都不能自动写回。
- 单源上游契约是另一条路径：必须记录提供方、接口/协议、版本、上游路径和项目适配器到响应字段的精确映射。仅有官网页面标签或相似字段名不能替代 API 字段路径证据。公式裁决也独立于日常碰撞。
- 来源质量审计显示 registry 有 2,560 条来源路径、973 条 `verified`，其中 773 条语义元数据可用、200 条需要元数据复核。这 200 条是显式复核缺口；按当前代码不会因缺少元数据而重新进入破解目标，也不应被用作锚。
