## 核验步骤

1. **确定接口与样本身份**：分别盘点 `np/get` 与 `stock/get` 的请求参数、响应包日期/`as_of_date`、原始字段是否存在、空值占比和字段类型；逐日区分 `-`、空、0 和缺字段。
2. **从归档重建事实**：只纳入日期可验证、股票身份可对齐的历史 raw；按有效交易日分组，去除重复快照，报告每个字段的覆盖率、不同值、稳定性和来源窗口。不得把 push2 的数据当作 ulist 原值。
3. **先验证接口关系，再判断语义**：检验 ulist 字段是否跨日精确对应某个已定义路径；独立输出路径映射证据和语义候选。恒空、恒 `-` 或无有效样本时，结论应是“当前接口样本不足/占位”，不能强行赋予同号字段含义。
4. **使用外部契约**：若公开接口说明或公开上游实现明确给出参数/字段定义，保存可定位的版本、URL 或 commit 和对应字段证据；来源相同的另一个接口可帮助解释，但不能冒充独立来源确认。
5. **生成逐路径裁决建议**：对 `f107`、`f118` 分别给出身份关系、候选含义、单位、有效日期覆盖、证据等级、反例和替代解释。两字段不要求得出相同结论。
6. **达到门槛后再闭环**：按 `ADJUDICATION_WORKFLOW.md` 更新 `source_fields`；运行字段文档生成器、unknown queue 和 registry parity；检查聚合字段是否从逐源记录正确生成。证据不足则保留未知状态并登记下一步证据需求。
