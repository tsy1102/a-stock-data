# Fuyao 官方契约与逐源登记核对（2026-10-18）

## 结论

Fuyao 的官方文档覆盖了接口和响应字段，但“官方文档完整”不等于项目中每条 `(source, 完整 code path)` 已自动绑定到某个响应字段。项目登记还包含接口容器、历史别名、计算路径和多接口共用的叶键；此外，旧碰撞状态曾把逐源 `verified` 与同短 code 的聚合 `unverified` 混成 `conflict`。

本次对登记的 223 条 Fuyao 路径逐条比对日期化的全量契约快照和适配器路由，只把有唯一响应键与接口对应的 69 条来源字段按契约定为 `verified`。其中 9 条解除的是聚合状态造成的假冲突，13 条同时更正了旧规范名、释义或单位。**没有新增跨源映射**，因此没有把“Fuyao 自身定义明确”误写成“与其他来源数值等价”。

## 已应用的变更

- 将 60 条 `unverified` 与 9 条可唯一绑定的状态冲突字段升级为 `verified_by_source_contract`。
- 修复 9 条状态冲突：其参考证据均为 `verified`，冲突只来自兼容聚合记录仍为 `unverified`，且没有字段属性冲突。
- 对 13 条字段保留原值快照并纠正元数据。包括把 `profit_total` 明确为“利润总额”、把 `total_debt` 按官方 `total_debt` 响应字段改为“负债合计”，以及把旧缩写或 F10 注记从单位栏换成契约给出的“原币元”。
- 不新增 `mappings`。契约核验确认的是 Fuyao 自身字段，不宣称其他来源字段与它相等。
- 更新后 Fuyao 状态为 `verified` 85、`unverified` 122、`conflict` 16；未知队列从 207 条降至 138 条，减少 69 条（33.3%）。

25 条原 `status_conflict` 全部是逐源参考状态与聚合状态不一致，并无 `attribute_conflicts`；其中 9 条有足够精确的契约与路径证据，因此已安全解除。剩余 16 条虽然知道冲突源于聚合视图，但目前没有唯一的契约响应键映射，故仍留在队列中，避免把状态错误修复变成字段语义猜测。

## 为什么仍有未知字段

`fuyao_api_full.md` 是接口契约，不是项目注册表的逐路径映射表。项目实际登记路径可能是 `ability.index_id`、计算层输出、历史短路径或一个接口对象；而适配器也可能返回带 `calculate_` 前缀的原始指标键。只看中文注释、变量名或字段名相似度，无法证明运行路径就是契约叶字段。

所以剩下的 138 条必须继续按 CSV 的原因逐项补证：多接口同名字段先确认接口，未匹配字段先追到具体适配器响应或历史别名转换，`calculate_*` 字段则需用实际响应键与上游实现核对。它们不会因“Fuyao 是官方接口”这一来源身份而自动消失。

## 影响与验证边界

本次只更新字段 adjudication 能力、字段注册表和生成的治理文档；没有改采集路由、请求频率、缓存键或生产数据映射。`field_source_reference.md` 等历史材料未改写。source-contract 结论与跨源关系仍是两个独立维度，后续碰撞只有在逐源状态、来源谱系、完整路径及数值证据都满足规则后，才登记跨源 mapping。

契约快照来自官方完整文档，项目记录的快照日期为 2026-08-22；本次核对针对该快照及当前适配器代码，没有进行在线接口抽样，也不把契约定义当作当前服务可用性的证明。
