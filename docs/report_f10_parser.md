# f10_parser.py 代码审查报告

## 概览
`f10_parser.py` 负责解析公开的财务报告（F10）数据并转换为统一结构，代码量约 19KB。整体实现功能完整，但在可维护性、类型安全、异常处理等方面仍有提升空间。

## 主要代码质量问题
1. **缺少类型注解**：函数参数/返回值均未使用 typing，导致调用方难以推断数据结构。
2. **文档不足**：几乎没有 docstring，函数名虽能表达意图，但缺乏输入/输出说明。
3. **异常捕获过宽**：大量使用 `except Exception` 捕获后仅打印日志，可能掩盖真实错误。
4. **重复解析逻辑**：多个解析函数在处理 HTML/JSON 时存在相似的正则或 `re.sub` 步骤，可抽取为通用工具函数。
5. **硬编码字符串**：如 HTML 标签、字段映射写死在代码中，难以适配数据源变化。
6. **性能细节**：在大文件（上万行）上使用 `re.findall` 循环处理，会产生不必要的临时列表。

## 改进建议
- 为每个公开函数添加完整的 `def func(arg: Type) -> ReturnType:` 注解；可使用 `TypedDict` 描述返回的字典结构。
- 编写模块级 docstring，列出支持的报表类型、返回数据 schema，以及使用示例。
- 将通用的 HTML 清理、数值转换抽象为内部 `_clean_html(text: str) -> str`、`_to_float(val: Any) -> float` 等工具函数。
- 使用 `logging` 替代 `print`，并在捕获异常后 `raise` 原异常或包装为自定义 `F10ParseError`，便于上层统一处理。
- 将硬编码的字段映射移动到 `f10_fields.yaml`（或常量字典），并在初始化时加载，便于后期维护。
- 对于大文本的正则处理，考虑使用 `re.finditer` 逐行匹配或借助 `BeautifulSoup` 进行结构化解析，以降低内存峰值。

## 风险评估
- **改动规模**：中等（约 200 行增量 + 重构部分函数），对现有 CLI 调用影响有限。
- **回归风险**：低，只要保持返回结构不变并添加完整单元测试即可。
- **收益**：提升代码可读性、降低后期维护成本；增加类型检查后可在 CI 中捕获潜在错误。
