## 一、背景与目标

### 1.1 背景

通过 `0x06B9` 协议从通达信服务器下载 `zhb.zip` 全局配置总包，解压后可获得 44 个静态数据文件，覆盖全市场股票的板块归属、行业分类、估值指标、资金流向等数据。

**核心优势**：
- 一次 TCP 请求（约 2.7 秒），拿到全市场静态数据
- 90% 是纯文本格式，解析成本极低
- 完全本地查询，零限流风险
- 结构性数据（板块成分、行业分类）几个月才变一次，延迟完全不影响

### 1.2 目标

1. **减少 HTTP 请求依赖**：将板块、行业、成分股等查询从东财 HTTP 切换到本地 zhb 解析
2. **提升全市场扫描效率**：val 脚本全市场扫描速度提升 5-10 倍
3. **增强数据维度**：新增申万行业分类等专业数据
4. **降低被封风险**：减少东财/同花顺等第三方 HTTP 接口调用

## 四、风险控制措施

### 4.1 数据新鲜度校验

每次下载 zhb 后：
1. 读取 tdxstat.cfg 首行的统计日期
2. 与当前日期对比，延迟 > 2 天输出警告
3. 延迟 > 3 天自动尝试切换节点重试

### 4.2 多节点轮询策略

```
优先节点（更新快）:
  - 招商证券深圳主站
  - 国信证券深圳主站
  - 中信证券上海主站
备用节点（更新慢）:
  - 各种边缘节点
```

### 4.3 降级策略

```
zhb 可用且新鲜 → 使用 zhb 数据
zhb 可用但较旧 → 使用 zhb + 标注日期 + 重要数据实时校验
zhb 不可用 → 自动降级回原有 HTTP/TCP 方案
```

## 五、文件管理策略

### 5.1 存储目录

```
项目根目录/
├── cache/
│   └── zhb/                    # zhb 专用缓存目录（.gitignore 忽略）
│       ├── zhb_20260714.zip    # 按数据日期命名的原始 zip（~1.4 MB）
│       ├── zhb_20260713.zip
│       ├── zhb_20260712.zip
│       └── ...
```

**目录说明**：
- `cache/zhb/` 与测试用的 `zhb/` 目录分离，生产环境用 cache 目录
- `cache/` 整体加入 `.gitignore`，不会污染仓库
- 测试脚本和探索性代码保留在 `zhb/` 目录

### 5.2 命名规则（彻底解决重名问题）

| 文件类型 | 命名格式 | 示例 |
|----------|---------|------|
| 原始 zip | `zhb_{YYYYMMDD}.zip` | `zhb_20260714.zip` |
| spblock 解析缓存（如有） | `spblock_{YYYYMMDD}.pkl` | `spblock_20260714.pkl` |
| tdxstat 解析缓存（如有） | `tdxstat_{YYYYMMDD}.pkl` | `tdxstat_20260714.pkl` |

**日期定义**：文件名中的日期是 **数据的日期**（tdxstat.cfg 首行的统计日期），不是下载日期。
- 例：7月14日下载到的是7月13日的数据 → 文件名为 `zhb_20260713.zip`
- 同一天下载多次，只要数据日期相同，就是同一个文件，不会重名

### 5.3 生成逻辑（完整流程）

```
调用 get_zhb_data()
        │
        ▼
  检查今日是否已有缓存
  (内存缓存优先，其次文件缓存)
        │
      ┌─┴─┐
      是   否
      │    │
      ▼    ▼
  直接返回    从通达信下载
  已有数据    zhb.zip（多节点轮询）
      │        │
      │        ▼
      │    读取 tdxstat 首行的统计日期
      │    作为文件名日期
      │        │
      │        ▼
      │    保存到 cache/zhb/zhb_{date}.zip
      │    （下载时写 .tmp 临时文件，写完再 rename）
      │        │
      │        ▼
      │    清理 7 天前的旧文件
      │        │
      └────┬───┘
           ▼
      内存解压解析
           │
           ▼
      返回各字段数据
      + 内存缓存结果
```

**关键设计点**：

1. **懒加载**：只有真正用到 zhb 数据时才下载，不用不下载
2. **同日幂等**：同一天调用 100 次，也只下载 1 次
3. **进程安全**：下载时加文件锁，防止多进程同时下载同一个文件
4. **下载失败不崩溃**：返回空数据 + 自动降级到原有 HTTP/TCP 接口
5. **临时文件机制**：下载到 `.tmp` 文件，写完再 rename，避免程序崩溃产生不完整文件

### 5.4 保留策略

| 数据级别 | 保留时长 | 原因 |
|----------|---------|------|
| 原始 zip 文件 | **7 天** | 占空间极小（7天×1.4MB ≈ 10MB），留着方便回溯排查问题 |
| 内存解析结果 | **进程内缓存** | 同一进程内多次调用，解析结果缓存到内存，不用每次都解压 |

**为什么是 7 天？**
- 够长：周末+节假日也覆盖到了，不会因为连休几天就没缓存
- 够短：不会无限增长占用磁盘
- 够用：排查一周内的问题都能找到对应日期的数据

**为什么不每次运行都删？**
- 太浪费：同一天可能运行多次脚本，删了又要重新下载
- 没好处：1.4 MB 一个文件，完全不占空间
- 失价值：留着可以对比数据变化、排查问题

### 5.5 清理逻辑

**触发时机**：每次成功下载**新的** zhb 文件之后（同一天重复调用不会触发清理）

**清理范围**：`cache/zhb/` 目录下，修改时间早于 7 天前的所有 `.zip` / `.pkl` / `.tmp` 文件

**清理算法**：
```python
import os, time

def _cleanup_old_zhb(cache_dir, keep_days=7):
    """清理N天前的旧zhb文件"""
    cutoff = time.time() - keep_days * 86400
    for fname in os.listdir(cache_dir):
        fpath = os.path.join(cache_dir, fname)
        if not os.path.isfile(fpath):
            continue
        # 只清理我们自己生成的文件（.zip / .pkl / .tmp）
        if not (fname.endswith('.zip') or fname.endswith('.pkl') or fname.endswith('.tmp')):
            continue
        if os.path.getmtime(fpath) < cutoff:
            try:
                os.remove(fpath)
            except OSError:
                pass  # 清理失败不影响主流程
```

**安全措施**：
1. **限定后缀**：只删 `.zip` / `.pkl` / `.tmp`，不会误删其他文件
2. **限定目录**：路径严格限定在 `cache/zhb/`，不会删到别处
3. **异常保护**：清理失败打个日志就行，不影响主流程

### 5.6 手动清理

除了自动清理，也可以用现有的 `scripts/clean_cache.py` 脚本手动清理：

```bash
# 清理所有缓存（包括 zhb）
python scripts/clean_cache.py

# 只清理 zhb 缓存（如支持分类清理）
python scripts/clean_cache.py --type zhb
```

### 5.7 特殊情况处理

| 场景 | 处理方式 |
|------|---------|
| 同一天但数据更新了（罕见） | 文件名按数据日期命名，新数据是新日期，不会重名 |
| 下载到一半程序崩溃 | 下载时写 `.tmp` 临时文件，写完再 rename；下次检测到不完整的 `.tmp` 自动删除重下 |
| 多进程同时下载 | 文件锁机制，只有一个进程下载，其他等它下完直接读 |
| 节点返回旧数据 | 校验 tdxstat 的日期，如果不是预期日期，自动切换节点重试 |
| 磁盘空间不足 | 自动清理所有缓存，只保留最新的一个 |
